# 歯科クリニック向け 医療資材 検収・在庫管理システム

新規開業した歯科クリニックで、受付・医療資材の検収・在庫管理を担当した経験から生まれた Web システムです。
Excel（VLOOKUP・手計算）で行っていた業務を、**入力の手間とミスを減らし、欠品を事前に防ぐ**仕組みとして作り直しました。

- デモ：https://syosyo1234.github.io/dental-inventory/login.html （デモ用アカウントはログイン画面に表示）
- ※ データはすべて架空のものです。患者情報は一切扱いません。

---

## 1. 業務課題と解決策

| 現場の課題 | 原因 | このシステムでの解決 |
|---|---|---|
| 検収のたびに型番・メーカー名・製品名・規格を手入力。診療の合間に行うため時間がかかり、入力ミスも発生 | 同じ情報を毎回入力していた（Excel の VLOOKUP で一部対応） | **型番を入力するだけで資材情報を自動表示**。全角・小文字入力も自動で正規化。入力は「数量」と「検収日」だけ |
| 在庫数と使用状況がリアルタイムで分からず、まれに欠品が発生 | 在庫表の更新が手作業・後回しになりがち | **検収・使用を登録した瞬間に在庫を自動更新** |
| 「あと何日もつか」を Excel で手計算していた | 平均使用量の計算が属人的 | **実際の使用記録から平均使用量・在庫残存日数を自動計算**し、リードタイムと比較して**発注アラート**を表示 |
| 登録ミスを修正すると、何が起きたか分からなくなる | 記録の上書き・削除 | 履歴は**削除・変更不可**。誤登録は「取消」記録を追加して修正し、**修正の痕跡を残す** |

### 業務フロー

```
資材マスタ登録 → 検収登録 → 在庫自動加算 → 使用登録 → 在庫自動減算
                                   ↓
             平均使用量の計算 → 在庫残存日数 → 発注アラート → 発注済み → 次回検収で自動解除
```

## 3. 技術構成

| 区分 | 採用技術 | 理由 |
|---|---|---|
| フロントエンド | HTML / CSS / JavaScript（フレームワークなし、ES Modules） | 構成をシンプルにし、保守・説明しやすくするため |
| バックエンド・DB | Supabase（PostgreSQL） | 認証・データベース・API を一体で利用でき、サーバー管理が不要 |
| 認証 | Supabase Auth（メール＋パスワード、公開登録は無効） | 院内スタッフのみが利用する業務システムのため |
| 権限制御 | Row Level Security（RLS）＋ データベース関数内の権限チェック | 画面を改ざんされてもデータを守れるように、制御をデータベース側に置く |
| ホスティング | GitHub Pages | 静的ファイルのみで動作し、無料・長期間公開可能 |

```
ブラウザ（HTML/CSS/JS） ──HTTPS──→ Supabase
  ・画面表示、入力補助             ・Auth：ログイン
  ・公開用キーのみ保持             ・PostgREST：参照（RLS で保護）
                                   ・データベース関数：在庫の変更はすべてここで実行
```

## 4. 設計のポイント

### 4-1. データを3層に分離
| 層 | テーブル | 性質 |
|---|---|---|
| マスタ | `products`, `categories` | 基本的に変わらない資材情報 |
| 在庫 | `stocks` | 現在庫数。データベース関数からのみ更新 |
| 履歴 | `stock_transactions` | **追記専用**の台帳。トリガーで更新・削除を禁止 |

「現在庫数 ＝ 履歴の増減合計」が常に成り立つため、`supabase/99_check.sql` でいつでも整合性を検証できます。

### 4-2. 在庫更新の安全性（データベース関数で実装）
検収・使用・調整・取消はすべて PL/pgSQL 関数（RPC）で処理し、画面から在庫テーブルを直接更新できないようにしています。

1. **行ロック**（`SELECT … FOR UPDATE`）：同じ資材への同時登録は順番に処理 → 更新の取りこぼしなし
2. **トランザクション**：履歴の追加と在庫の更新は「両方成功」か「両方失敗」
3. **二重送信防止**：画面ごとに送信ID（UUID）を発行し、DB の一意制約で同じ登録を1回だけ処理
4. **マイナス在庫の禁止**：関数内のチェック ＋ テーブルの CHECK 制約の二重防御

> 検証結果：在庫10の資材に対して30接続から同時に1個ずつ出庫 → ちょうど10件成功・20件は「在庫不足」、最終在庫0。同じ送信IDで5回同時に検収 → 登録は1件のみ。

### 4-3. 平均使用量・在庫残存日数・状態判定
```
1日あたり平均使用量 ＝ 直近N日（7 or 30）の出庫合計 ÷ N    ※取消済みは除外
                     実績がなければ「手動設定値」、どちらもなければ「データ不足」
在庫残存日数         ＝ floor(現在庫 ÷ 平均使用量)          ※平均0・データ不足では計算しない
```
| 状態 | 条件（D=残存日数, L=リードタイム, S=安全在庫日数, Q=現在庫, R=発注点） | 意味 |
|---|---|---|
| 緊急：在庫不足 | Q = 0、または D ≤ L | 今発注しても到着前に欠品の恐れ |
| 注意：発注推奨 | D ≤ L + S、または Q ≤ R | 今発注すれば余裕をもって到着 |
| 正常：在庫十分 | 上記以外 | - |

計算はデータベース関数 `get_inventory_status` に集約し、ダッシュボード・在庫一覧・発注アラートで**必ず同じ結果**になるようにしています。

### 4-4. 権限
| 操作 | 未ログイン | スタッフ | 管理者 |
|---|---|---|---|
| 参照 | ✕ | ○ | ○ |
| 検収・使用・発注済み設定 | ✕ | ○ | ○ |
| マスタ登録・編集、在庫調整、取消 | ✕ | ✕ | ○ |
| テーブルの直接書き換え | ✕ | ✕ | ✕（関数経由のみ） |

フロントエンドには公開用キー（Publishable key）のみを置き、`service_role` / Secret key は使用していません。

## 7. 運用上の注意
Supabase の無料プランは、一定期間アクセスがないとプロジェクトが一時停止されます。デモ前に管理画面でプロジェクトの状態を確認し、停止している場合は再開（Resume）してください。停止中に画面を開くと「デモ環境が休止中の可能性があります」と表示されます。
